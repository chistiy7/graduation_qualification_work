# ЕДИНЫЙ РАБОЧИЙ ПАЙПЛАЙН (вход → обработка → выход)

## 0) Каналы входной информации (что ты мне даёшь)

**А) Текстовые задачи**
- Формат: 3–10 пунктов списком.
- На каждый пункт: что изменить / где / критерий готовности.
- Ссылки на файлы через `@path` (или точный путь).

**Б) Обратная связь преподавателя / научрука**
- Формат: «цитата замечания → к чему относится».
- Если есть документ/скрин: прикладывается или копируется текстом.
- Если замечание к оформлению: указать, где видно эталон (страница/пример).

**В) Аудио созвона**
- Вход: файл `.mp3/.m4a/.wav` + название сессии + (опционально) заметки.
- Запуск: из каталога `diploma` через `python3 -m context_service process ...`.
- Выход сервиса: `03_capture/sessions/YYYYMMDD_HHMM_<title>/`.

## 1) Артефакты по итогам созвона (что я должен сделать)

Для каждой сессии из `03_capture/sessions/...` формируются:
- `transcript.md` — полный транскрипт (с таймкодами).
- `context.md` — структурированное извлечение (если запуск без `--transcript-only`).

После появления `transcript.md` выполняются действия:
- **Брифинг встречи** (создаётся рядом с транскриптом): `briefing.md`.
  - Содержит только проверяемые пункты, без «воды».
  - Структура:
    - **Решения/договорённости** (что принято как факт)
    - **Правки в тексте** (где и что переписать)
    - **Новые требования к модели/ПО**
    - **Открытые вопросы** (что спросить в следующий раз)
- **Синхронизация контекста**:
  - Если добавлен новый термин/соответствие — обновляется `00_context/glossary.md`.
  - Если в диплом внесён новый аргумент, определение, метрика, допущение — обновляется `00_context/state.md` (раздел «Введённые аргументы»).

## 2) Контроль задач (как ведётся прогресс)

Единый «реестр состояния» — `00_context/state.md`.
- Любая завершённая крупная единица (глава/раздел/важный артефакт) фиксируется в `## Готово`.
- Любая начатая работа фиксируется в `## В работе` (коротко: что именно и где).
- Запрещено повторять в главах то, что уже перечислено в «Введённых аргументах», без добавления нового смысла.

Если преподаватель просит «переписать» — в `state.md` добавляется пункт в `## В работе` с источником замечания (откуда оно).

## 3) Обработка замечаний преподавателя (цикл правок)

На вход: список замечаний (см. п. 0Б).
На выход: 3 артефакта в ответе ассистента.
- **Таблица соответствия «замечание → правка → место»** (коротко, без лишних объяснений).
- **Список изменений по файлам**: какие файлы затронуты.
- **Критерий закрытия**: что должно получиться в тексте (формулировка/структура/оформление).

Правило: если замечание неоднозначно (можно трактовать 2+ способами), задаётся уточняющий вопрос до внесения правок.

## 4) Переход от теории к практике (рефакторинг `Shaft-production-planner-Main`)

Условие старта практики: теоретический контекст стабилизирован (главы 1–2 зафиксированы, введение/гл. 3–5 имеют план и требования из созвонов).

Режим работы по практике:
- Сначала формируется «матрица соответствия» предметной области:
  - **цех → лаборатория**, **изделие → образец**, **операция → испытание**, **маршрут производства → маршрут испытаний**, **рабочие зоны → лабораторные зоны**.
  - Источник истинных определений — `00_context/glossary.md`.
- Затем изменения в коде делаются итерациями по `02_structure/dev_plan.md` (MVP → [+]).
- После каждой итерации обновляется короткий статус в `00_context/state.md` и фиксируется, какие сущности/термины изменены в проекте.
